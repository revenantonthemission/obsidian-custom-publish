# Security Requirements — U3 `u3-writing-moves`

Upstream: `inception/requirements-analysis/requirements.md` (NFR1, NFR2, NFR3, NFR5, NFR6); `construction/u3-writing-moves/functional-design/functional-spec.md`, `rules.md`; `inception/contract-design/contract-summary.md` (C4, C5); codekb `technology-stack.md`.

## Context

U3 adds the only request-time behaviour in this release: the static server looks the incoming path up in a redirect table and, on a match, answers 301 with a `Location` header. The table is a file the build writes into the site output and the deploy copies to the web root, so it is public and attacker-readable, and the server trusts it enough to put its contents into a response header.

U3 handles no visitor input beyond the request path and its query string, keeps no secret, has no form, no session and no authentication, and writes no file at request time. The risks are an open redirect, a header injection through the table or the query, a redirect loop, a path traversal through the table, a server that trusts a broken table, a permanent redirect to an address that cannot be served, a third-party request, a page that only works with JavaScript, and a merge that breaks the existing suites. The accessibility and no-JavaScript requirements are recorded here as controls against the failure modes they prevent, following the precedent set by U4's security artifact.

| Threat | Control | Requirement |
|---|---|---|
| The server becomes an open redirect: a visitor-supplied path or host is copied into a `Location` header | the target comes only from the build-written table's `to`; the request contributes the lookup key and the query it appends, nothing else | NFR5.22 |
| A header injection through the query string, or an uncaught error in the request handler that takes the server down | the query is checked before anything is assembled — a query carrying percent-encoded control bytes is answered 400 and never written into a header — the assembled `Location` value is validated before it is written, and the request path never throws | NFR5.22 |
| A broken or hostile table puts a header value, a foreign origin or a loop into the response | the table is accepted only in the exact shape of contract C4; anything else means no redirect at all, one error line, no failed request | NFR5.23, NFR5.24 |
| The table's own file is read from outside the web root, or a rule points outside the site | the table path is fixed inside the web root; the existing containment check still guards every served file | NFR5.24 |
| A permanent redirect points at an address the server cannot serve | the clean-URL rewrite serves a resolved directory's `index.html`, so every tag page the build produced is servable at its own address; the writer emits a rule only for a page the build produced and checks the rule's target before the table is written, and the server answers 301 on every match without resolving the target again | NFR5.25 |
| The moved pages load a third-party resource, or the table is served as an executable type | same-origin only; the table is served as `application/json` from the site's own root | NFR2.4 |
| The moved pages or the graph's list panel depend on JavaScript | the pages are static markup; the graph's list panel is revealed by the graph stylesheet without JavaScript | NFR3.4 |
| An inaccessible marker, an invisible back link, a target too small | the existing accessibility bar: axe WCAG 2.2 AA at four widths in light and dark, one h1, 44 × 44 px targets | NFR1.15 |
| A merge that breaks the old-address expectations or the existing suites | the full verification command; the old expectations are updated, not deleted; the whole repository is re-grepped for the old address literals | NFR6.15, NFR6.16 |

## Requirements

| ID | Requirement | Verification | Source |
|---|---|---|---|
| NFR5.22 | The `Location` value is assembled from two parts and nothing else: the matched rule's `to`, each segment percent-encoded exactly once, followed by the request's query string appended byte-for-byte and never decoded or re-encoded. The query is checked before anything is assembled: a query whose raw bytes carry percent-encoded control bytes (`%00`–`%1f` and `%7f`, in any case) is answered 400 and never written into a header — the rejection reads the query's own characters and matches the encoded form, so the query is never decoded or re-encoded — and every other query is appended byte-for-byte. The assembled value is then checked against the characters an HTTP header may carry before it is written. No other visitor input — not the path, not the host header — reaches the header. The request path never throws out of the handler, because an uncaught error there would exit the process and take the blog down until launchd restarts it. A request whose path matches no rule answers the normal 404 — never a redirect. | Vitest over the redirect module and the HTTP-level checks: `/tags?x=%0d%0a` is answered 400 and the server keeps serving the next request; `//evil.example`, `/tags/..%2F..%2Fevil` and a percent-encoded host answer either the table's target or the 404; the query of a normal request is preserved byte-for-byte and never re-encoded | NFR5, BR3.2, BR3.3 |
| NFR5.23 | The table is accepted only when it satisfies contract C4 exactly: it parses as JSON, its version is 1, `rules` is a list, and every rule's `from` and `to` is a decoded absolute path without a trailing slash. A rejected table means the server serves files normally, answers no redirect and writes one error line; it never fails a request and never redirects to an address it cannot prove. The writer never emits a rule whose `to` is another rule's `from`, so the fixed rules cannot loop. | Vitest over the redirect module: a missing file, invalid JSON, an unknown version, a non-list `rules` and a rule with a relative or trailing-slash path are each rejected with no redirect and no failed request; the writer's own output is checked to hold no such pair | NFR5, BR3.4 |
| NFR5.24 | No redirect target leaves the site: a `to` that is not an absolute path (a scheme, a host or a relative path) is rejected with the whole table, and the server's existing containment check still applies to every file it serves, including the table itself, which is read from a fixed path inside the web root. | Vitest over the redirect module: a rule with `to: "https://elsewhere.example/"` or `to: "../x"` is rejected and no `Location` header is emitted | NFR5, BR3.4, C4 |
| NFR5.25 | A permanent redirect never points at an address the server cannot serve, and the server does not pay for that guarantee at request time. The unit extends the clean-URL rewrite so that a path which resolves to a directory inside the web root is served by that directory's `index.html`, whatever the path's shape, so every tag page the build produced is servable at its own address — including a tag key containing a dot (BR3.6). The writer emits a rule only for a tag page the build produced and checks the rule's target before the table is written, so the table carries no rule whose target the server cannot serve; the server then answers 301 on every match, as contract C4 states, and resolves no target at request time, so the request path stays flat (NFR4.10). One residual lies outside this requirement: the deploy copies the table before the page directories, so a request for a brand-new tag address in that window is answered 301 to a page that is not there yet — the deploy ordering that closes that window belongs to the infrastructure design. | the build-output check: every rule's `to` names a tag page the build produced; the HTTP-level checks: a dotted tag key's old address is answered 301 and its target is served; the request-path check observes that a matched request reads no file for the target | NFR5, BR3.1, BR3.4, BR3.6 |
| NFR2.4 | No changed page and no new file requests any origin other than the site's own. The three moved pages load nothing from another origin, and the redirect table is served as `application/json; charset=utf-8` from the site's own root. | the HIG origin check over the moved routes; the served content type of `_redirects.json` | NFR2, BR2.4, AC7.1.2 |
| NFR3.4 | With JavaScript off the tag index, the tag pages and the graph page show all their content and links, the graph's list panel is visible (the stylesheet rule that reveals it without JavaScript is part of the graph page's own stylesheet), and every control is keyboard reachable. `just crossunit` passes with only the fixture's deliberate broken image, and the link sweep reports no `/tags` or `/graph` link. | `just crossunit`, with the no-JavaScript smoke extended to the three moved routes and asserting the graph's list panel is visible; the link sweep over the built site | NFR3, BR4.3, BR4.4, AC7.1.3 |
| NFR1.15 | Every moved route (`/writing/tags`, `/writing/tags/<tag>`, `/writing/graph`) passes axe WCAG 2.2 AA at 320, 768, 1024 and 1440 px in light and dark plus the reduced-motion check; each page has exactly one h1, and the back link is a real link with a visible focus style and a target of at least 44 × 44 px. | the existing `HIG_ROUTES` axe matrix over the new addresses; the Playwright target and focus assertions | NFR1, BR1.2, BR4.1, AC7.1.1 |
| NFR6.15 | The existing suites stay green on the U3 merge: `cargo test --release`, `npm run test:unit`, `npm run test:pbt`, `npm run format:check`, `npx astro check` and the HIG Playwright suites. The old-address expectations are updated, not deleted — the HIG route list, the shared support file's `OPEN_STATES` entry that opens the graph's list tab, the tag and graph page checks, the Writing capsule checks, the search-from-tags check, the performance specification's Core Web Vitals and mobile-network route lists, and the profile specification's baseline routes. Before the merge the whole repository is re-grepped for the `/tags` and `/graph` address literals, so no expectation is missed. | the recorded Construction Verification Command; the repository-wide grep for `'/tags'` and `'/graph'` literals, with every hit either updated or confirmed as a data path (`/graph.json`) | NFR6, BR4.4, AC7.1.4 |
| NFR6.16 | Every redirect acceptance criterion is evidenced at HTTP level, not only inside the module: a request against the running server asserts the status, the `Location` header value and the kept query for `/tags`, `/tags/`, `/graph`, `/graph/`, `/tags/<tag>` and `/tags/<tag>/`, that `/graph.json` is served as a file, that an unknown tag is answered 404, and that a hostile query is answered 400 without taking the server down.
 The harness is the one the HIG suite already runs — the production server over `site/dist` on 127.0.0.1:4329 — so the evidence comes from the shipped server, not a test double. The dotted tag key has its own named subject, because no tag key in the vault or in the fixtures contains a dot: the server's own Vitest check starts the production server against a temporary web root that holds a synthetic dotted tag page (`writing/tags/node.js/index.html`) and a table carrying the matching rule (`/tags/node.js` → `/writing/tags/node.js`), then asserts that the old address is answered 301 and that the target is served (not 404) through the directory rewrite. The synthetic subject needs no vault fixture and no change to the published site. | the HTTP-level checks in the HIG suite against the running server; the server's Vitest check over the temporary web root for the dotted key; the module-level Vitest covers the pure functions and the table validation | NFR6, BR3.2, BR3.3, BR3.4, BR3.5, BR3.6, AC5.2.1–AC5.2.5 |
