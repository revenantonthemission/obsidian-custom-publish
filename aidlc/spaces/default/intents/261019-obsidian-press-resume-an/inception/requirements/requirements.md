## 2. 제품 목표와 성공 기준

### 2.1 제품 목표

채용 담당자, 협업 상대, 블로그 독자가 한 사이트 안에서 운영자의 경력, 역량, 작업 방식, 대표 프로젝트를 신뢰할 수 있게 파악하도록 한다. 임시 외부 Notion 링크를 사이트 내부의 정식 이력서와 포트폴리오 경험으로 교체하면서도 기존 블로그의 정적 생성 구조와 성능 특성을 유지한다.

### 2.2 주요 사용자

- 짧은 시간 안에 경력과 역량을 판단하려는 채용 담당자
- 기술적 의사결정과 협업 방식을 확인하려는 개발자 및 잠재 협업자
- 글의 작성자와 운영 프로젝트를 더 알고 싶은 블로그 독자
- 한 곳의 데이터로 프로필 콘텐츠를 관리하려는 사이트 운영자

### 2.3 성공 기준

1. `/resume`와 `/portfolio`가 한국어 정적 페이지로 생성되고 홈페이지에서 명확히 접근 가능하다.
2. 두 페이지는 저장소 안의 타입이 있는 공용 데이터 한 벌을 사실의 단일 원본으로 사용한다.
3. 포트폴리오는 사실 검수를 마친 대표 프로젝트 3~6개를 완전한 case study 구조로 제공한다.
4. 이력서는 화면 탐색, 브라우저 인쇄, 버전 관리되는 PDF 다운로드를 모두 지원한다.
5. `passion-project`는 홈페이지 원본으로만 쓰이며 일반 글 URL, 검색, RSS, sitemap에 중복 노출되지 않는다.
6. 관련 빌드, 예제 기반 테스트, property-based test, Playwright smoke test가 통과하고 PBT가 CI에서 재현 가능한 seed와 함께 실행된다.
7. 기존의 관련 없는 로컬 변경을 보존하며, 배포와 AWS 변경은 수행하지 않는다.

## 4. 범위

### 4.1 포함

- 저장소가 소유하는 타입 기반 공용 프로필 데이터와 빌드 시 검증
- 한국어 `/resume`와 `/portfolio` 정적 페이지
- 요약과 확장 상세를 결합한 이력서
- 대표 프로젝트 3~6개의 case study 포트폴리오
- 공개 이메일과 GitHub CTA
- 이력서 print CSS 및 버전 관리되는 다운로드 PDF
- 페이지별 검색·공유 메타데이터와 적절한 구조화 데이터
- 홈페이지 소개 및 두 내부 페이지 CTA
- 외부 Vault의 `Areas/Notes/Passion Project.md`에 한정된 링크·홈페이지 콘텐츠 수정
- `passion-project`의 홈페이지 전용 처리와 명시된 일반 노출면 제외
- 기능에 필요한 Rust/Astro 소스 변경과 생성물 재생성
- 관련 예제 기반 테스트와 전체 적용 모드의 property-based test
- Astro build와 Playwright 반응형·접근성·인쇄 smoke test
- PBT가 실행될 수 있도록 하는 최소 Jenkins 경로 수정, 테스트 단계, seed 기록

### 4.2 범위 밖

- 위 최소 CI 예외와 홈페이지 전용 처리에 필요하지 않은 Jenkins 및 전처리기 부채 정리
- Terraform 또는 AWS 인프라 변경
- Security Baseline에서 발견했던 기존 인프라·공급망·관측성 항목 해결
- Resiliency Baseline 적용
- 영어 또는 다국어 페이지
- 연락 폼, 외부 API, 외부 임베드, 새 이미지 CDN
- 새 클라이언트 JavaScript 또는 새 외부 런타임 의존성
- 사이트 전체 디자인 시스템 재구축
- 사용자가 승인하지 않은 개인·경력·교육·자격·성과 정보 공개
- 배포, S3 업로드, CloudFront invalidation 또는 기타 AWS mutation

## 5. 기능 요구사항

### FR-001 — 공용 프로필 데이터

1. 이력서와 포트폴리오는 저장소 안의 타입이 있는 공용 구조화 데이터 한 벌을 canonical source로 사용해야 한다.
2. 이름, 소개, 연락처, 경력, 기술, 프로젝트 등 공유 사실을 페이지별로 중복 관리해서는 안 된다.
3. 데이터 구조는 필수값, 선택값, 순서, URL, 대표 프로젝트 개수 같은 도메인 제약을 빌드 또는 테스트 시 검증할 수 있어야 한다.
4. 잘못된 데이터가 조용히 누락된 페이지를 만들지 않도록 유효하지 않은 필수 데이터는 명확한 오류로 빌드를 실패시켜야 한다.

### FR-002 — 사실 근거와 콘텐츠 승인

1. 초기 콘텐츠 초안은 공개 GitHub 정보와 이 저장소에서 확인 가능한 이력을 근거로 작성해야 한다.
2. 공개 출처만으로 증명할 수 없는 고용 관계, 직함, 기간, 학력, 자격, 수치 성과, 개인적 역할 또는 결과를 추정하거나 만들어서는 안 된다.
3. 공개 이메일, GitHub 계정, 경력, 프로젝트 선정, 프로젝트별 역할·성과·결과는 공개 전 사용자의 명시적 사실 검수를 받아야 한다.
4. 검수되지 않은 placeholder 또는 예시 사실이 프로덕션용 페이지나 PDF에 실제 사실처럼 남아서는 안 된다.

### FR-003 — 내부 페이지와 언어

1. 사이트는 `/resume`와 `/portfolio`라는 독립된 내부 경로를 제공해야 한다.
2. 두 페이지의 사용자 대면 콘텐츠는 한국어로 제공해야 한다.
3. 두 페이지는 직접 URL 접근과 정적 사이트 빌드 결과에서 모두 정상적으로 열려야 한다.
4. 각 페이지는 기존 사이트의 공통 헤더, 테마, 기본 탐색 문맥 안에서 현재 위치와 목적을 이해할 수 있어야 한다.

### FR-004 — 이력서 경험

1. 이력서는 첫 화면에서 핵심 소개, 역량, 주요 경력 또는 대표 성과를 빠르게 파악할 수 있는 요약을 제공해야 한다.
2. 사실 검수를 마친 세부 경력과 성과는 사용자가 필요할 때 펼쳐 볼 수 있어야 한다.
3. 확장 기능은 정적 HTML의 기본 동작과 접근 가능한 시맨틱을 우선 사용해야 한다.
4. 데이터가 존재하지 않거나 검수되지 않은 교육·자격 등의 섹션을 억지로 생성해서는 안 된다.
5. 화면용 이력서, 인쇄 결과, 다운로드 PDF 사이의 핵심 사실은 일치해야 한다.

### FR-005 — 포트폴리오 case study

1. 포트폴리오는 사용자가 최종 승인한 대표 프로젝트 3개 이상 6개 이하를 제공해야 한다.
2. 각 case study는 최소한 다음 내용을 포함해야 한다.
   - 해결하려던 문제
   - 사용자의 역할
   - 핵심 의사결정
   - 시스템 또는 구현 구조
   - 확인 가능한 결과
   - 배운 점
3. 저장소, 운영 페이지 또는 관련 글 링크는 실제로 존재하고 공개 가능한 경우에만 제공해야 한다.
4. 프로젝트 나열 순서는 공용 데이터에서 명시적으로 관리되고 모든 빌드에서 결정적이어야 한다.

### FR-006 — 연락 CTA

1. 이력서와 포트폴리오에서 사용자가 승인한 공개 이메일과 GitHub 링크를 명확한 연락 CTA로 제공해야 한다.
2. 실제 이메일 주소와 GitHub identity는 구현 중 사용자 검수 없이 추정해서는 안 된다.
3. 연락 CTA는 키보드와 보조 기술로 이름과 목적을 이해하고 실행할 수 있어야 한다.

### FR-007 — 페이지별 시각 방향

1. 이력서는 인쇄 가독성과 정보 위계를 우선하는 절제된 시각 디자인을 사용해야 한다.
2. 포트폴리오는 case study의 문제·결정·구조·결과를 구분해 탐색할 수 있는 더 시각적인 구성을 사용해야 한다.
3. 두 페이지 모두 기존 사이트의 `--c-` CSS 변수, 공통 헤더, 라이트·다크 테마와 조화를 유지해야 한다.
4. 장식은 콘텐츠 이해, 접근성, 인쇄 품질 또는 정적 성능을 훼손해서는 안 된다.

### FR-008 — 홈페이지 통합

1. 홈페이지의 현재 임시 Portfolio 링크 영역은 짧은 자기소개와 Résumé·Portfolio CTA 카드로 교체해야 한다.
2. CTA는 외부 Notion URL이 아니라 새 내부 `/resume`, `/portfolio`를 가리켜야 한다.
3. 구현 단계에서 외부 Vault의 `Areas/Notes/Passion Project.md`만 범위를 제한해 수정할 수 있다.
4. 외부 Vault의 다른 문서나 첨부파일은 이 요구사항의 편집 범위가 아니다.

### FR-009 — `passion-project` 홈페이지 전용 처리

1. `Passion Project.md`의 콘텐츠는 홈페이지 원본으로 계속 사용할 수 있어야 한다.
2. `/posts/passion-project` 일반 글 페이지는 생성되거나 공개되어서는 안 된다.
3. 해당 항목은 일반 글 목록, 검색 인덱스, RSS, sitemap에서 제외해야 한다.
4. 파생 요구사항으로, 다른 일반 글 탐색면이 이 항목을 보통의 게시물로 다시 노출해서는 안 된다. 구체적으로 어느 파생 데이터가 해당하는지는 Application Design에서 기존 파이프라인을 기준으로 확정한다.
5. 홈페이지 전용 처리 방식은 generated artifact를 직접 고치는 방식이 아니라 authored source와 전처리 규칙에서 선언적이고 재현 가능해야 한다.

### FR-010 — 인쇄와 PDF

1. `/resume`는 브라우저 인쇄에 최적화된 print CSS를 제공해야 한다.
2. 인쇄 결과는 불필요한 탐색 및 화면 전용 장식을 숨기고, 텍스트 잘림과 의도하지 않은 주요 섹션 분리를 피해야 한다.
3. 사이트는 사용자가 승인한 이력서의 다운로드 PDF를 제공해야 한다.
4. PDF는 버전 관리되어야 하며 링크가 빌드 결과에서 유효해야 한다.
5. PDF 파일명, 저장 경로, 생성 또는 갱신 절차는 Application Design에서 정한다.

### FR-011 — 메타데이터와 구조화 데이터

1. `/resume`와 `/portfolio`는 각각 고유한 title, description, canonical URL을 가져야 한다.
2. 두 페이지는 각각의 목적에 맞는 Open Graph 및 Twitter 카드 메타데이터를 제공해야 한다.
3. 각 페이지에는 승인된 사실만 사용하는 적절한 구조화 데이터를 제공해야 한다.
4. 구조화 데이터의 schema.org 타입은 Application Design에서 페이지 의미와 실제 데이터 가용성을 바탕으로 정한다.
5. canonical 및 공유 URL은 운영 도메인 규칙과 일관되어야 한다.

### FR-012 — 탐색과 교차 연결

1. 홈페이지에서 이력서와 포트폴리오로 이동할 수 있어야 한다.
2. 이력서와 포트폴리오는 서로 또는 공통 탐색을 통해 자연스럽게 전환할 수 있어야 한다.
3. 내부 링크는 정적 빌드 결과에서 유효해야 하며, 기존 블로그 탐색을 방해해서는 안 된다.

### FR-013 — 정적 동작 원칙

1. 새 페이지와 CTA는 정적 HTML/CSS를 우선해야 한다.
2. 이 기능을 위해 새 client-side JavaScript 또는 Preact island를 추가해서는 안 된다.
3. 이 기능을 위해 외부 런타임 API나 새 외부 런타임 의존성을 추가해서는 안 된다.
4. 확장 상세, 테마, 링크, 인쇄 같은 핵심 기능은 JavaScript 없이 사용할 수 있어야 한다.

### FR-014 — 예제 기반 검증

1. Astro production build가 성공해야 한다.
2. `/resume`, `/portfolio`, 홈페이지 CTA, 메타데이터, PDF 링크, `passion-project` 제외를 단언하는 자동 테스트를 제공해야 한다.
3. Playwright smoke test는 최소한 대표적인 좁은 화면과 넓은 화면에서 페이지 접근과 레이아웃 핵심을 확인해야 한다.
4. Playwright smoke test는 키보드 접근, 명확한 접근 가능한 이름, 주요 포커스 동작, reduced-motion 처리의 대표 시나리오를 확인해야 한다.
5. Playwright smoke test는 이력서의 인쇄 미디어 핵심 동작을 확인해야 한다.
6. 정확한 viewport와 브라우저 matrix는 Application Design 또는 테스트 설계에서 정한다.

### FR-015 — Property-Based Testing

1. 전체 적용 모드로 PBT-01부터 PBT-10까지 해당 AI-DLC 단계에서 강제해야 한다.
2. Functional Design은 각 비즈니스 규칙, 데이터 변환, 직렬화, 필터링에 대해 testable property를 식별하거나 적용 불가 근거를 기록해야 한다.
3. PBT 적용 언어마다 custom generator, 자동 shrinking, seed 재현, 기존 test runner 통합을 지원하는 framework를 NFR Requirements에서 선택해야 한다.
4. 도메인 generator는 유효한 한국어·Unicode 텍스트, URL, 선택 필드, 경계값, 프로젝트 개수와 같은 실제 제약을 반영해야 한다.
5. PBT는 예제 기반 테스트를 대체하지 않으며, 주요 사용자 시나리오는 두 방식으로 상호 보완해 검증해야 한다.
6. PBT가 발견한 최소 실패 사례는 적절한 경우 영구 예제 기반 회귀 테스트로 고정해야 한다.

### FR-016 — 최소 CI 변경

1. 현재 저장소 구조와 맞지 않는 Jenkins의 Rust manifest 또는 binary 경로를 PBT와 관련 품질 게이트가 실행될 수 있는 최소 범위에서 수정해야 한다.
2. Jenkins는 이 기능에 적용되는 예제 기반 테스트와 property-based test를 실행해야 한다.
3. CI의 모든 PBT 실행은 seed를 항상 출력하거나 고정 seed를 사용해 실패를 재현할 수 있어야 한다.
4. 자동 shrinking을 비활성화해서는 안 되며 실패 출력에 최소 반례를 확인할 수 있어야 한다.
5. 이 요구사항은 Jenkins 파이프라인 전반의 리팩터링, 배포 변경 또는 관련 없는 기존 부채 해결을 허용하지 않는다.

### FR-017 — source/generated 경계

1. 기능 동작은 `preprocessor/`, `site/src/`, 외부 Vault의 허용된 단일 문서, 설정·테스트 같은 authored source에서 구현해야 한다.
2. `content/`, `site/dist/`, Rust `target/`, 생성되는 `site/public` JSON 또는 assets를 유일한 동작 원본으로 직접 수정해서는 안 된다.
3. 필요한 생성 결과는 문서화된 전처리 및 빌드 명령으로 재현해야 한다.
4. 기존의 관련 없는 작업 트리 변경을 덮어쓰거나 작업에 흡수해서는 안 된다.

### FR-018 — 배포 경계

1. 요구사항 승인, 설계, 구현, 테스트 완료는 배포 승인을 의미하지 않는다.
2. 사용자가 별도로 명시하지 않는 한 `just deploy`, AWS 또는 Terraform mutation을 실행해서는 안 된다.

## 6. 비기능 요구사항

### NFR-001 — 접근성

- WCAG 2.2 AA를 설계·검증 목표로 삼는다. 이는 자동 테스트만으로 완전한 준수 인증을 보장한다는 의미가 아니다.
- 페이지는 논리적인 제목 구조, landmark, 목록, 링크, 버튼 또는 `<details>`와 같은 의미에 맞는 요소를 사용해야 한다.
- 모든 핵심 흐름은 키보드로 사용할 수 있고 포커스가 시각적으로 보여야 한다.
- 텍스트와 인터랙티브 요소는 AA 목표에 맞는 명도 대비를 가져야 한다.
- 모션이 있다면 `prefers-reduced-motion`을 존중하고, 모션 없이도 같은 정보를 제공해야 한다.
- 인쇄본과 PDF도 읽기 순서와 텍스트 가독성을 유지해야 한다.

### NFR-002 — 반응형 사용성

- 좁은 모바일 화면부터 넓은 데스크톱 화면까지 가로 스크롤이나 핵심 콘텐츠 잘림 없이 사용할 수 있어야 한다.
- 긴 한국어 문장, URL, 기술명, 프로젝트 제목이 레이아웃을 깨뜨리지 않아야 한다.
- 고정 breakpoint와 테스트 viewport는 설계 단계에서 기존 사이트 규칙을 확인한 뒤 결정한다.

### NFR-003 — 성능

- 새 페이지의 핵심 콘텐츠는 빌드 시 생성된 HTML에 포함되어야 한다.
- 기능 때문에 새 client-side JavaScript bundle이나 외부 런타임 요청을 추가하지 않는다.
- 이미지 또는 다이어그램을 사용한다면 적절한 크기, 대체 텍스트, 레이아웃 안정성을 고려해야 한다.
- 기존 정적 사이트의 캐시 가능성과 빠른 최초 콘텐츠 표시 특성을 유지해야 한다.

### NFR-004 — 유지보수성

- 공유 사실은 공용 데이터에서 한 번만 수정하면 관련 페이지, 메타데이터, 테스트, PDF 갱신 흐름에 일관되게 반영될 수 있어야 한다.
- 데이터 type, validation, 렌더링 책임은 이해 가능한 경계로 분리해야 한다.
- 새 CSS는 기존 `--c-` 변수와 컴포넌트 관례를 재사용하고 페이지별 예외를 명확히 제한해야 한다.
- 홈페이지 전용 문서 규칙은 파일명에만 의존하는 숨은 예외보다 명시적이고 테스트 가능한 표현을 우선한다.

### NFR-005 — 테스트 가능성과 재현성

- 테스트는 네트워크나 외부 서비스의 가용성에 의존하지 않아야 한다.
- 정적 데이터와 렌더링 결과는 같은 입력에서 결정적으로 생성되어야 한다.
- PBT는 domain generator, shrinking, seed 기반 재현성을 제공해야 한다.
- 실패한 품질 게이트는 문제 경로 또는 규칙을 식별할 수 있는 출력과 non-zero exit status를 제공해야 한다.

### NFR-006 — 검색 및 공유 품질

- 메타데이터는 페이지별로 중복되지 않고 실제 표시 콘텐츠와 모순되지 않아야 한다.
- 구조화 데이터는 유효한 JSON-LD이며 승인된 사실만 포함해야 한다.
- `passion-project`의 홈페이지 전용 상태가 일반 검색·피드 노출로 새지 않아야 한다.

### NFR-007 — 콘텐츠 무결성과 개인정보

- 공개 연락처와 개인 이력은 사용자가 공개를 승인한 값만 사용해야 한다.
- 정량 성과는 확인 가능한 근거와 사용자의 승인이 없으면 표시하지 않는다.
- 외부 링크는 안전한 URL 형식이어야 하며 존재하지 않는 링크를 CTA로 제공하지 않는다.

### NFR-008 — 호환성

- JavaScript가 비활성화되어도 핵심 콘텐츠, 링크, 확장 상세, 인쇄가 동작해야 한다.
- 지원 범위는 현재 사이트가 목표로 하는 현대 브라우저와 Astro의 정적 출력 범위를 유지한다.
- 구체적인 브라우저 matrix는 기존 프로젝트 설정과 Playwright 도입 방식을 검토한 뒤 설계 단계에서 확정한다.

### NFR-009 — 인쇄·PDF 품질

- 인쇄본은 A4를 포함한 일반적인 문서 출력 환경에서 핵심 콘텐츠를 읽을 수 있어야 한다.
- 색상에만 의미를 의존하지 않고 흑백 또는 제한된 색상 출력에서도 정보 위계가 유지되어야 한다.
- 다운로드 PDF와 웹 이력서 사이의 사실 불일치는 완료를 막는 결함으로 취급한다.
- PDF 생성·검증 절차는 반복 가능하고 문서화되어야 한다.

### NFR-010 — 품질 게이트

- Rust 전처리기 변경에는 `just test`가 필요하다.
- 사이트 변경에는 `cd site && npx astro build`가 필요하다.
- 교차 파이프라인 변경은 안전한 작업 트리 조건에서 `just build`를 사용하고, 그렇지 못하면 `just test`와 `just site-build`를 실행한 뒤 end-to-end fixture pipeline을 건너뛴 구체적 이유를 기록한다.
- 기능별 예제 기반 테스트, PBT, Playwright smoke test와 최소 Jenkins 검증 결과를 Build and Test 산출물에 기록한다.
- 검증 과정에서 배포 명령을 사용하지 않는다.

## 7. 사용자 시나리오

### USCN-001 — 채용 담당자의 빠른 이력 확인

1. 사용자가 홈페이지의 Résumé CTA를 선택한다.
2. `/resume`에서 핵심 소개와 경력 요약을 즉시 파악한다.
3. 필요한 세부 경력과 성과를 키보드 또는 포인터로 펼쳐 본다.
4. GitHub로 이동하거나 공개 이메일을 사용해 연락한다.
5. 브라우저에서 인쇄하거나 승인된 PDF를 내려받는다.

### USCN-002 — 협업자의 프로젝트 판단

1. 사용자가 홈페이지 또는 공통 탐색에서 Portfolio CTA를 선택한다.
2. `/portfolio`에서 대표 case study 3~6개를 탐색한다.
3. 각 프로젝트의 문제, 역할, 결정, 구조, 결과, 배운 점을 확인한다.
4. 제공되는 경우 공개 저장소나 관련 글로 이동한다.
5. GitHub 또는 이메일 CTA로 연락한다.

### USCN-003 — 블로그 독자의 일반 탐색

1. 독자가 홈페이지에서 운영자 소개와 새 프로필 CTA를 본다.
2. 일반 게시물 목록, 검색, RSS 또는 sitemap을 탐색한다.
3. 홈페이지 원본인 `passion-project`를 별도의 일반 게시물로 중복해서 만나지 않는다.
4. 기존 블로그 글과 탐색 흐름은 새 프로필 기능 때문에 손상되지 않는다.

### USCN-004 — 운영자의 콘텐츠 갱신

1. 운영자가 저장소의 공용 프로필 데이터 한 벌을 수정한다.
2. 잘못된 필수값, URL, 중복 식별자, 허용 범위를 벗어난 프로젝트 수가 검증에서 실패한다.
3. 올바른 변경은 이력서, 포트폴리오 및 관련 메타데이터에 일관되게 반영된다.
4. 관련 예제 테스트와 PBT가 로컬 및 CI에서 실행되고 실패 seed를 재현할 수 있다.
5. PDF를 갱신해야 하는 변경은 문서화된 절차로 확인된다.

## 9. 제약, 의존성, 미확정값

### 9.1 구현 전 제약

- feature branch는 프로젝트 Git Flow에 따라 `develop`에서 분기하고 완료 후 `--no-ff`로 `develop`에 병합한다.
- 2026-07-23 로컬 기준 `main`과 `develop`은 각각 반대편에 113개와 8개의 commit이 있는 diverged 상태이므로 지금은 feature branch 생성을 차단한다.
- Workflow Planning에서 `develop`이 `main`과 원격 기준에 비추어 현재의 안전한 base인지 검증하고, 필요하면 history rewrite나 파괴적 조작 없는 해결 절차를 먼저 승인해야 한다.
- 기존 dirty working tree의 사용자 변경은 보존해야 한다.
- 외부 Vault 수정은 사용자 요구사항상 허용됐지만, 실행 환경 권한이 필요하면 구현 단계에서 해당 단일 파일에 한정해 승인을 받아야 한다.

### 9.2 설계 단계에서 확정할 항목

- 공용 프로필 데이터의 정확한 type 및 validation schema
- 홈페이지 전용 문서를 표현하고 전처리하는 구체적 메커니즘
- PDF 파일명, 저장 경로, 생성·갱신·시각 검증 절차
- 실제 구조화 데이터 schema.org 타입
- PBT 적용 언어별 framework
- Playwright 브라우저, viewport 및 print 검증 방식
- 최종 컴포넌트 경계와 CSS 구성

### 9.3 사용자 사실 검수가 필요한 값

- 공개 이메일 주소
- 공개 GitHub identity 및 URL
- 이름, 직함, 소개 문구
- 경력, 기간, 역할, 교육, 자격
- 대표 프로젝트 3~6개의 최종 선정과 순서
- 프로젝트별 역할, 핵심 결정, 구조, 성과, 결과, 배운 점
- 모든 정량 지표와 외부 링크

이 값들은 설계 결정을 위한 placeholder와 구분해야 하며, 사용자 승인 전에는 최종 공개 콘텐츠로 간주하지 않는다.

## 10. 검증 및 완료 조건

### 10.1 수용 기준과 증거

| 수용 기준 | 최소 증거 |

| 공용 typed data 사용 | type/validation 소스와 공유 소비 테스트 |
| 사실 검수 완료 | 사용자의 명시적 콘텐츠 승인 기록 |
| 대표 case study 3~6개 | schema validation과 렌더링 assertion |
| 홈페이지 CTA 및 Notion 제거 | Vault source diff와 홈페이지 링크 테스트 |
| `passion-project` 홈페이지 전용 | 일반 route, search, RSS, sitemap 제외 테스트 |
| 접근성 목표 | semantic review 및 Playwright 키보드·포커스·reduced-motion smoke 결과 |
| 반응형 레이아웃 | 좁은 화면과 넓은 화면 Playwright smoke 결과 |
| 인쇄와 PDF | print-media smoke, PDF 링크 검사, 렌더링 시각 검증 |
| 메타데이터 | head/JSON-LD assertion 및 유효성 확인 |
| PBT 전체 적용 | 적용 단계별 PBT compliance, generator/property test, shrinking 및 seed 증거 |
| CI 실행 | Jenkins 경로·테스트 단계 검증과 seed 출력 |
| 회귀 없음 | `just test`와 사이트 또는 교차 파이프라인 build gate 결과 |
| 배포 경계 준수 | 배포·AWS mutation이 없었다는 완료 기록 |

### 10.3 완료 정의

다음 조건을 모두 만족해야 이 기능을 완료로 간주한다.

1. 사용자가 요구사항, 설계, 실제 공개 사실을 각각 해당 게이트에서 승인한다.
2. 필수 기능 및 비기능 요구사항에 대응하는 구현과 검증 증거가 있다.
3. 예제 기반 테스트와 전체 적용 PBT가 상호 보완되며 CI에서도 실행된다.
4. 관련 Rust, Astro, Playwright, 링크, 인쇄·PDF 검증이 통과한다.
5. 관련 없는 사용자 변경과 generated/source 경계가 보존된다.
6. 완료된 AI-DLC 산출물은 새 workflow 시작 전에 고유한 `docs/aidlc/runs/YYYY-MM-DD-<slug>/`로 보관한다.
7. 사용자가 별도로 요청하지 않은 배포나 AWS 변경은 수행하지 않는다.
