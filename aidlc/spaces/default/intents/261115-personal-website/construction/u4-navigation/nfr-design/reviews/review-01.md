### Summary

The design's core controls hold up against the code: the fail-closed path really is existing code (`navigation.model.invalid` and `navigation.current.invalid` in `site/src/lib/profile/issues.ts` lines 35–36 and 77–78; `normalizeNavigationHref` rejects control characters, whitespace, bad percent escapes, encoded slashes, backslashes and double slashes; `Header.astro` line 16 throws `TypeError('Invalid primary navigation state.')`), the sheet is already a static `<details>` with no client directive, the page-behind rule is the existing `visibility: hidden` rule in `chrome.css` lines 319–323, the tokens and shared resources named in `logical-components.md` all exist, the site loads no third-party resource (the jsDelivr entries in `profile-resources.ts` are an unused legacy type), and the CSS byte baseline reproduces exactly. The main weakness is the security design's test plan: two existing expectations break under the one-item model and neither appears in the table, so a developer following the plan exactly gets a red suite and must work out the new expectations unaided.
