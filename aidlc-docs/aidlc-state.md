## Post-Approval Review Fix — Release Lock Silent Failure

- **Finding**: `acquireReleaseLock().release()` swallowed the `unlink` failure with `.catch(() => {})` and is called on the **success** path by `finalizeResumeRelease`. A failed unlink therefore left a lock file behind while the caller believed the lock was gone. Because a stale lock is deliberately never broken, every later release fails `RELEASE_LOCK_HELD`. The wedge was diagnosable — `resume:pdf:verify` reported `lockPresent: true` — but the operator could not distinguish **"crashed mid-release, needs rollback"** from **"finalize succeeded, only the unlink failed, safe to delete the lock"**, and those demand opposite actions. The information separating them was discarded at the `.catch`.
- **Fix, part 1 (`release-store.mjs`)**: `release()` still never throws, because it runs in cleanup paths where an exception would mask the failure that led there. It now records the fault instead of discarding it, returns `{lockFileRemoved, fault}`, and exposes the last outcome as `releaseOutcome`. `finalizeResumeRelease` surfaces `lockFileRemoved` and `lockFault` on its result rather than throwing, since the release itself genuinely completed.
- **Fix, part 2 (`verification-provider.mjs`)**: `verifyCurrentRelease` no longer collapses both states into `RELEASE_INCOMPLETE`. A lock with **no journal** is now `RELEASE_LOCK_ORPHANED` with an actionable message, because the journal is removed only at finalize — so its absence is precisely the signal that the release completed. A journal present remains `RELEASE_INCOMPLETE`. Both still throw, so the command still fails closed.
- **Verification**: 15 files / 181 tests (two new regressions plus one amended: `release()` now resolves to the outcome rather than `undefined`, which the old idempotency assertion caught). `npx astro check` 0 errors / 6 inherited hints after adding the missing `verifyCurrentRelease` declaration to `verification-provider.d.mts`.
