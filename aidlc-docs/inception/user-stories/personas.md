## 문서 목적

이 문서는 승인된 요구사항을 사용자 중심 stories로 변환하기 위한 역할형 archetype을 정의한다. Personas는 실제 개인이나 인구통계 가정을 표현하지 않으며, 확인되지 않은 운영자의 경력·신원·성과 사실을 포함하지 않는다.

## PER-01 — 신속 심사형 채용 담당자

### Context

여러 후보 또는 협업 대상을 비교하는 과정에서 사이트에 방문한다. 처음에는 짧은 시간 안에 핵심 적합성을 판단하고, 관심이 생기면 상세 경력과 보관 가능한 이력서를 확인한다.

### Goals

- 첫 화면에서 역할, 역량, 주요 경력 또는 승인된 성과의 핵심을 파악한다.
- 필요한 세부 경력만 선택적으로 확인한다.
- 신뢰할 수 있는 연락 수단을 찾는다.
- 검토용 이력서를 읽기 좋은 형태로 인쇄하거나 PDF로 보관한다.

### Motivations

- 중요한 정보를 빠르게 비교할 수 있는 명확한 정보 위계
- 요약을 뒷받침하는 구체적이면서 검수된 상세
- 화면, 인쇄본, PDF 사이의 사실 일관성
- 목적이 명확한 이메일 및 GitHub CTA

### Key Questions

- 이 사람의 핵심 역량과 관련 경험은 무엇인가?
- 요약을 뒷받침하는 역할과 결과를 더 확인할 수 있는가?
- 표시된 사실과 링크를 신뢰할 수 있는가?
- 다음 검토를 위해 이력서를 보관하거나 연락할 수 있는가?

### Constraints and Frictions

- 첫 판단에 사용할 시간이 제한적일 수 있다.
- 장식이 정보 위계를 가리거나 긴 서술만 제공되면 비교하기 어렵다.
- 키보드, 인쇄, PDF 환경에서도 같은 핵심 정보가 필요하다.
- 검수되지 않은 수치나 깨진 링크는 전체 프로필의 신뢰를 낮춘다.

### Success State

핵심 이력을 빠르게 이해하고, 관심 있는 상세를 검토한 뒤, 승인된 연락 경로로 이동하거나 내용이 일치하는 인쇄본·PDF를 확보한다.

### Mapped Stories

- ST-U01 — 홈페이지에서 프로필 발견과 이동
- ST-U02 — 핵심 이력 판단과 상세 검토
- ST-U03 — 이력서 사본 인쇄·다운로드
- ST-U05 — 공개 근거 확인과 연락

## PER-02 — 증거 중심 개발자·잠재 협업자

### Context

블로그, 검색 결과, 공유 링크 또는 홈페이지를 통해 방문한다. 기술 목록 자체보다 실제 문제, 역할, 의사결정, 구조, 결과와 배운 점의 연결을 살펴 협업 가능성을 판단한다.

### Goals

- 대표 프로젝트 3~6개를 비교해 관심 있는 case study를 찾는다.
- 각 프로젝트에서 실제 역할과 핵심 의사결정의 맥락을 이해한다.
- 확인 가능한 결과와 공개 근거를 살펴본다.
- GitHub 또는 이메일을 통해 다음 대화로 이동한다.

### Motivations

- 기술적 결정의 이유와 trade-off가 드러나는 설명
- 문제부터 결과와 배운 점까지 이어지는 완전한 case study
- 실제로 존재하고 공개 가능한 저장소, 운영 페이지 또는 관련 글
- 기존 블로그와 일관되지만 case study에 적합한 시각적 탐색

### Key Questions

- 어떤 문제를 어떤 역할로 해결했는가?
- 구조와 핵심 결정은 무엇이며 왜 그렇게 선택했는가?
- 결과는 확인 가능하고 과장되지 않았는가?
- 더 살펴볼 공개 근거나 연락 경로가 있는가?

### Constraints and Frictions

- 프로젝트 수가 너무 많거나 구조가 제각각이면 비교하기 어렵다.
- 역할과 결과가 모호하면 기술적 기여를 판단할 수 없다.
- 존재하지 않거나 공개할 수 없는 링크는 제공되지 않아야 한다.
- 긴 한국어 설명과 기술명이 좁은 화면에서도 읽혀야 한다.

### Success State

선별된 case studies에서 문제 해결 방식과 기술적 판단을 비교하고, 필요한 공개 근거를 확인한 뒤, 적절한 연락 경로로 이동한다.

### Mapped Stories

- ST-U01 — 홈페이지에서 프로필 발견과 이동
- ST-U04 — 대표 프로젝트와 작업 방식 판단
- ST-U05 — 공개 근거 확인과 연락

## PER-03 — 맥락 탐색형 블로그 독자

### Context

특정 글이나 홈페이지를 읽다가 작성자가 누구이며 어떤 일을 하는지 궁금해진다. 프로필은 자연스럽게 발견하고 싶지만 기존 글 탐색, 검색, RSS와 sitemap이 프로필 기능 때문에 혼란스러워지는 것은 원하지 않는다.

### Goals

- 홈페이지에서 작성자와 사이트의 전문적 맥락을 짧게 이해한다.
- 관심에 따라 이력서 또는 포트폴리오로 이동한다.
- 일반 글 목록과 검색·피드에서 실제 게시물을 계속 탐색한다.
- 홈페이지 원본 콘텐츠를 별도 게시물로 중복해서 만나지 않는다.

### Motivations

- 블로그 흐름을 방해하지 않는 간결한 소개
- 목적이 분명한 내부 Résumé·Portfolio CTA
- 동일 콘텐츠가 홈페이지와 일반 게시물로 중복되지 않는 정보 구조
- JavaScript와 관계없이 동작하는 기본 탐색

### Key Questions

- 이 글을 쓰는 사람은 어떤 일을 하는가?
- 이력과 프로젝트 중 어디에서 더 알아볼 수 있는가?
- 일반 글 탐색 결과에 홈페이지용 콘텐츠가 왜 다시 나타나는가?
- 기존 블로그 탐색은 그대로 신뢰할 수 있는가?

### Constraints and Frictions

- 외부 Notion 링크는 사이트 문맥과 탐색 연속성을 끊는다.
- 홈페이지 원본이 일반 글, 검색, RSS, sitemap에 중복되면 콘텐츠 구조가 혼란스럽다.
- 프로필 기능이 기존 게시물 목록이나 탐색을 손상해서는 안 된다.

### Success State

홈페이지에서 내부 프로필 경로를 발견하고 필요할 때 이동하며, 일반 글·검색·피드에서는 홈페이지 전용 원본의 중복 없이 블로그를 계속 탐색한다.

### Mapped Stories

- ST-U01 — 홈페이지에서 프로필 발견과 이동
- ST-U06 — 중복 없는 블로그 탐색

## PER-04 — 정확성 책임 사이트 운영자

### Context

이력서, 포트폴리오, 홈페이지, 메타데이터, 인쇄·PDF가 서로 다른 사실을 말하지 않도록 관리한다. 공개 출처로 만든 초안과 실제 공개 가능 사실을 구분하고, 변경이 배포 전 자동 검증되는지를 확인한다.

### Goals

- 공용 프로필 데이터 한 벌에서 공유 사실을 관리한다.
- 누락, 잘못된 URL, 중복 식별자, 프로젝트 개수 위반을 빌드 전에 발견한다.
- 신원, 연락처, 경력, 프로젝트 역할·성과를 명시적으로 검수한다.
- 홈페이지 전용 콘텐츠와 일반 게시물의 노출 경계를 재현 가능하게 유지한다.
- 웹·인쇄·PDF의 핵심 사실 일치와 품질 게이트 실행을 확인한다.
- PBT 실패를 seed와 최소 반례로 로컬 및 CI에서 재현한다.

### Motivations

- 중복 수정과 사실 불일치를 줄이는 single source of truth
- 잘못된 콘텐츠를 조용히 생략하지 않는 명확한 실패
- authored source와 generated artifact의 분명한 경계
- 예제 기반 테스트와 PBT가 보완하는 재현 가능한 품질 증거
- 관련 없는 부채나 배포로 범위가 확장되지 않는 안전한 변경

### Key Questions

- 한 번의 유효한 변경이 모든 관련 공개 결과에 일관되게 반영되는가?
- 잘못된 값과 검수되지 않은 사실이 공개 전에 차단되는가?
- 홈페이지 원본은 유지되면서 일반 탐색면에서는 확실히 제외되는가?
- 웹, 인쇄, PDF가 같은 승인 사실을 보여주는가?
- CI 실패를 같은 seed와 shrunk counterexample로 재현할 수 있는가?

### Constraints and Frictions

- 공개 GitHub와 저장소 이력만으로 개인적 역할이나 성과를 추정할 수 없다.
- 외부 Vault 편집 범위는 `Areas/Notes/Passion Project.md` 하나로 제한된다.
- dirty working tree의 관련 없는 사용자 변경을 보존해야 한다.
- `main`과 `develop`의 안전성 확인 전에는 feature branch를 만들 수 없다.
- 구현·검증 완료는 배포 승인을 의미하지 않는다.

### Success State

승인된 단일 입력은 이력서, 포트폴리오, 홈페이지 관련 출력과 메타데이터에 결정적으로 반영된다. 유효하지 않은 입력, 공개 사실 불일치, 노출 경계 회귀, PDF 문제, PBT 실패는 재현 가능한 증거와 함께 공개 전에 차단된다.

### Mapped Stories

- ST-E01 — 공용 프로필 데이터의 일관된 관리
- ST-E02 — 승인된 사실만 공개
- ST-E03 — 재현 가능한 예제·PBT 품질 검증
- ST-E04 — CI에서 동일한 품질 게이트 실행

## Persona 사용 원칙

- Stories는 위 persona의 목표와 관찰 가능한 성공 상태를 표현한다.
- Personas에 나이, 지역, 회사, 직함, 학력 등 승인되지 않은 인구통계나 실제 사실을 추가하지 않는다.
- 구현 우선순위, 일정, sprint 또는 컴포넌트 소유권을 persona 문서에서 결정하지 않는다.
- 실제 콘텐츠 사실은 별도의 사용자 검수 게이트를 통과해야 한다.
