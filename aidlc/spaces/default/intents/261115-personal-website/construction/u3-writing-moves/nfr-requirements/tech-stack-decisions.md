# Tech Stack Decisions — U3 `u3-writing-moves`

Upstream: codekb `technology-stack.md`; `construction/u3-writing-moves/functional-design/frontend-components.md`, `rules.md`, `functional-spec.md`; `inception/requirements-analysis/requirements.md` (NFR2, NFR3, NFR4, NFR5, NFR6); `inception/contract-design/contract-summary.md` (C4, C5); team Code Style.

U3 adds no dependency, no runtime and no new file type. The stack stays as it is: Astro 7.4.1 with server-rendered pages, Node ESM tooling under `site/scripts/`, Vitest for unit and property tests, and Playwright plus axe for the browser checks. The decisions below are about where the new logic lives and how it is proven.

| Area | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| Writing the redirect table | An Astro integration's `astro:build:done` hook, registered in the site's Astro config, writes `_redirects.json` into the build's own output directory — the hook's `dir` argument, the way the profile integration already resolves its own output — after the pages are built. The production build's output directory is `site/dist`, so the nightly rsync copies the table to the web root with the rest of the output | the table reaches the build output with no pipeline change (`just site-build` and the Jenkins Build Site step keep running `npx astro build`), and resolving the directory from the hook keeps the writer correct for every build, including an isolated `--outDir` build (NFR4.9, NFR6.13) | a site endpoint `src/pages/_redirects.json.ts` (the router skips underscore-prefixed files under `src/pages`, so it would never emit the table); an npm `postbuild` script (`npx astro build` does not run npm lifecycle hooks); a new Justfile and Jenkinsfile step (two places to keep in step for one file); a hard-coded `site/dist` path (the repository's own builds write to an isolated `--outDir`, so a fixed path would drop the table into a shared directory that the current build never produced) |
| Where the table's rules come from | The built tag pages: the writer reads the `writing/tags/<key>/` directories the build just produced, so one rule exists per tag page and the rules and the pages cannot drift (NFR4.9). The unit extends the server's clean-URL rewrite so that a path resolving to a directory is served by that directory's `index.html`, so every built tag page is servable and no tag key is excluded; a rule is emitted for every tag page the build produced, the writer checks the rule's target before the table is written, and the server answers 301 on every match without resolving the target again (NFR5.25, amended). | one source of truth for the rules and the pages; no second reader of the published metadata; every rule's target is provably servable, because the server serves every directory the build produced and the writer checks the target before it ships | reading `content/meta/*.json` again in the writer (a second metadata reader and a second place where the tag list can differ from the pages); a rule for every tag key without the server fix (a dotted key would redirect to an address the server answers 404 for); a request-time check of every redirect target (a file-system read on the redirect path, and a server that answers something other than 301 on a match, which contract C4 does not allow) |
| Where the table is checked | The build-output check runs against an **isolated** build: the unit suite's build helper writes the site to its own `--outDir` (`site/tests/unit/support/astro-build.ts`) and the check reads the table from that directory; in Build and Test it reads the output that stage produced. The shared `site/dist` is never the subject of the check | the repository's own build-output tests deliberately avoid `site/dist` so they run wherever the unit suite runs, including the Jenkins Verify stage, which runs before the Build Site stage; a check against the shared directory would read whichever build happened to be there, or nothing at all in CI (NFR4.9) | checking the shared `site/dist` (in CI the file does not exist when the check runs, and locally it reads an unrelated build); a dedicated build in the check (a second build per check run, and a second lock wait) |
| The shared address rule | One dependency-free ES module with a `.d.mts` declaration beside it, imported by the TypeScript pages and by the plain-Node build hook: it owns the old and the new address of one tag key, in decoded and in once-encoded form | one implementation of the sanitization and of every address, readable from both worlds (BR2.1, BR2.2); the `.mjs` + `.d.mts` pair is the pattern the repo already uses for its Node tooling | a TypeScript-only module (the build hook is plain Node and cannot import it); a second copy of the rule for the writer (two sources for one address) |
| The redirect logic | Its own module, `site/scripts/redirect-table.mjs`, imported by the server script: `loadRedirectTable(tablePath, { readFile, stat })`, `matchRedirect`, `redirectLocation`. The loader takes the table path plus injectable `readFile` and `stat` functions; the server passes its own defaults | the module is pure, so a unit test imports it without starting a server; the injectable seam is what makes the read count observable (NFR4.10); the server script keeps its `listen` at module scope exactly as launchd runs it today | the logic inside `local-server.mjs` (the module scope calls `server.listen(PORT, HOST)`, so a test import would bind the production blog's port 8080 and serve the real web root); a main guard in the server script (a main guard would keep the launchd entry a plain script — the repository already uses that pattern — but the separate module avoids the question entirely and keeps the logic importable without touching the server's entry contract) |
| Proving the redirects | Module-level Vitest for the pure functions and the table validation, plus HTTP-level checks against the production server the HIG suite already runs (`site/dist` on 127.0.0.1:4329), including the hostile-query case that must be answered 400 without taking the server down | the acceptance criteria are stated at HTTP level ("answers 301 with `Location: …`", "the query string is kept"), so the evidence has to be an actual response (NFR6.16); the existing harness needs no new server | module-level assertions only (they cannot observe the status, the header or the kept query); a new test framework or a test-double server (no new dependency, and a double would not prove the shipped server) |
| The moved pages | Astro server-rendered pages at their new addresses; a shared `BackLink.astro` component for the "‹ Writing" link; the back link's rules live in `site/src/styles/grouped.css`, the stylesheet the three moved pages already load, which Astro inlines into their `<style>` block while its minified content stays under the build's 4096-byte inline limit (`build.assetsInlineLimit`) — measured at 3631 B minified before the move and about 3909 B with the back-link rules added, leaving roughly 187 B of headroom — so the back link adds no stylesheet request and no file under the hashed asset directory (NFR6.14). That stylesheet is inlined into every page that loads it, so no file under the hashed asset directory carries its bytes and the rule move changes those inline blocks only: no hashed file is added or renamed. A build or unit check fails when the combined stylesheet reaches the limit, and the rules move to a stylesheet of their own if it ever does, so later growth cannot turn the inline block into a hashed request silently; the graph keeps its existing island and its own stylesheet | no new island and no new runtime (NFR2.4), the pages work without JavaScript (NFR3.4), one implementation of the back link, and no new request on the moved routes (NFR6.14); the guard keeps that last property true as the shared stylesheet grows | a client-side router or an island-based redirect (adds JavaScript, fails NFR3.4); a stylesheet-only solution for the back link (not a link); the moved pages importing `site/src/styles/writing.css` (a new request and a changed hashed-asset set on every moved route, for rules they could carry in the stylesheet they already load) |
| The table's format | JSON at version 1, exactly as contract C4 states: `from` and `to` are decoded absolute paths without a trailing slash, the rules sorted and unique | the contract is owned by U3 and the deployed server reads this file, so the shape is fixed for this release (NFR5.23) | a second table format for the local server; a hand-maintained list of old addresses (it would drift from the tag list) |
| Cross-unit edit | U3 also switches `/writing/all` — U2's page — to the shared back-link component: one markup refactor, no behaviour change, and U3 owns it. U3 also moves the `.back-link` and `.back-link-chevron` rules out of `site/src/styles/writing.css` — U2's stylesheet, shared with the `/writing` pages — into `site/src/styles/grouped.css`, which the three moved pages already load, so the moved routes gain no stylesheet request (NFR6.14) | one implementation of the back link; U2's page is otherwise untouched, and the unit is built after U2 in this workflow; the rule move is declared here because it touches a stylesheet U2's pages share | leaving the duplicate inline markup on `/writing/all` (two implementations of one rule); editing anything else of U2's page; leaving the rules in `writing.css` and importing that stylesheet on the moved pages (a new request on every moved route) |
| Out of scope | No change to the preprocessor, the publish boundary, the `/writing` landing page, the primary navigation or the deployment pipeline | contracts C1, C2 and C3 stay with their owners; the build command and the rsync step stay as they are | — |
